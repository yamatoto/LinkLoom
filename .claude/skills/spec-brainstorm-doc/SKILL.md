# Spec Brainstorm & Documentation

このスキルは、要件定義や仕様についてのブレインストーミングを支援し、会話を自動的に構造化ドキュメントとして保存します。

## このスキルができること

1. **Socratic Dialogue（ソクラテス式対話）**: 深掘り質問で要件を明確化
2. **壁打ち支援**: アイデアや仕様について対話的に思考を整理
3. **自動ドキュメント化**: 会話の内容を構造化して`docs/ai-memo/`に保存
4. **トレードオフ分析**: 複数の選択肢とそれぞれのメリット・デメリットを明確化
5. **決定事項の記録**: 設計判断の根拠と背景を残す

## ワークフロー

### 1. ブレストの開始

ユーザーが要件定義や仕様について話し始めたら、このスキルが自動的に起動します。

**起動トリガー:**
- 「〜の要件を考えたい」
- 「〜の仕様について壁打ちしたい」
- 「〜の機能をどう実装するか悩んでいる」
- 「〜についてブレストしたい」

### 2. Socratic Dialogue（深掘り質問）

以下の観点から体系的に質問を投げかけ、要件を明確化します：

#### A. 背景・目的の明確化
- **なぜ**: なぜこの機能が必要なのか？
- **誰のため**: 誰が使うのか？主要なユーザーは？
- **課題**: 現在どんな問題があるのか？
- **ゴール**: 何が達成できれば成功か？

#### B. 機能・範囲の定義
- **Must Have**: 絶対に必要な機能は？
- **Should Have**: あると良い機能は？
- **Nice to Have**: 将来的に追加したい機能は？
- **Out of Scope**: 今回やらないことは？

#### C. 制約・前提条件
- **技術制約**: 使用する技術スタックは？
- **性能要件**: レスポンスタイム、スループットの要件は？
- **セキュリティ**: 機密性、アクセス制御の要件は？
- **既存システム**: 既存の機能との関係は？

#### D. データモデル・API設計
- **データ構造**: どんなデータを扱うのか？
- **入出力**: APIの入力と出力は？
- **バリデーション**: どんな検証が必要か？
- **エラーハンドリング**: どんなエラーケースがあるか？

#### E. トレードオフと代替案
- **選択肢**: 実装方法の候補は？（最低2つ）
- **メリット**: それぞれの利点は？
- **デメリット**: それぞれの欠点は？
- **推奨**: どれを選ぶべきか、なぜか？

#### F. テスト戦略
- **テストケース**: どんなケースをテストすべきか？
- **エッジケース**: 境界値や異常系は？
- **パフォーマンステスト**: 負荷試験は必要か？

### 3. 会話の整理と要約

ブレストが進むにつれて、以下を定期的に要約します：

- これまでに決まったこと
- まだ決まっていないこと
- 次に議論すべきこと

### 4. 一区切りの検出

以下のタイミングで「会話をドキュメント化しますか？」と提案します：

- 主要な決定事項が出揃った
- ユーザーが「これで良さそう」と言った
- 会話が自然な区切りに達した
- ユーザーが明示的に「まとめて」と言った

### 5. 自動ドキュメント化

会話の内容を構造化して`docs/ai-memo/`に保存します。

**ファイル名形式:**
```
docs/ai-memo/YYYY-MM-DD_テーマ名.md
```

**例:**
- `docs/ai-memo/2025-10-18_user-notification-feature.md`
- `docs/ai-memo/2025-10-18_api-rate-limiting-design.md`

**ドキュメント構成:**
```markdown
# [機能名・テーマ]

**日時**: YYYY-MM-DD
**参加者**: Claude, [ユーザー名]

## 背景・目的

## 要件定義

### Must Have（必須）

### Should Have（あると良い）

### Out of Scope（今回やらないこと）

## 設計方針

### データモデル

### API設計

## 検討した代替案

### 案A: [案名]
- **メリット**:
- **デメリット**:

### 案B: [案名]
- **メリット**:
- **デメリット**:

## 採用した設計と理由

## テスト戦略

## 残課題・TODO

## 参考リンク
```

## 使用例

### 例1: 新機能の要件定義

```
ユーザー: ユーザー通知機能の要件を考えたいんですが
```

スキルが自動的に：
```
Claude: ユーザー通知機能について一緒に考えましょう。
まず、なぜこの機能が必要なのか教えていただけますか？

[ユーザーとの対話...]

Claude: これまでの議論を整理すると:
- 目的: ユーザーへのリアルタイム通知
- 対象: すべてのログインユーザー
- 通知タイプ: システム通知、個人宛通知

次に、通知の配信方法について考えましょう。
リアルタイム（WebSocket）とバッチ処理（メール）、
どちらが適切だと思いますか？

[対話が続く...]

Claude: 一区切りつきましたね。会話の内容を
`docs/ai-memo/2025-10-18_user-notification-feature.md`
にドキュメント化しますか？
```

### 例2: API設計の壁打ち

```
ユーザー: 検索APIの設計について壁打ちしたい
```

スキルが自動的に：
```
Claude: 検索APIの設計について一緒に考えましょう。
まず、どんなデータを検索するAPIですか？

[対話...]

Claude: なるほど、ユーザー検索ですね。
検索条件はどのようなものを想定していますか？
- 名前
- メールアドレス
- スキル
- 登録日

[対話...]

Claude: ページネーションはどうしますか？
- Offset-based（offset + limit）
- Cursor-based（cursor + limit）

それぞれのメリット・デメリットを整理しましょう。
```

### 例3: アーキテクチャ判断の記録

```
ユーザー: Lambda関数を分割するか悩んでいる
```

スキルが自動的に：
```
Claude: Lambda関数の分割について考えましょう。
現在の状況を教えていただけますか？
- 現在のLambda関数のサイズは？
- 実行時間は？
- どの部分を分割したいですか？

[対話...]

Claude: 分割案を2つ考えてみましょう：

**案A: 機能別に分割**
- メリット: ...
- デメリット: ...

**案B: レイヤー別に分割**
- メリット: ...
- デメリット: ...

どちらが良いと思いますか？
```

## 質問の深掘りパターン

このスキルは、以下のような質問パターンを使って思考を深めます：

### 5W1H
- **Why（なぜ）**: なぜその機能が必要？
- **What（何を）**: 何を実現したい？
- **Who（誰が）**: 誰が使う？
- **When（いつ）**: いつ使う？リアルタイム？バッチ？
- **Where（どこで）**: どこで動く？クライアント？サーバー？
- **How（どうやって）**: どうやって実現する？

### 問題の本質を探る
- 「そもそも、この問題はなぜ発生している？」
- 「本当に解決すべき問題は何？」
- 「この機能がなかったらどうなる？」

### 範囲の明確化
- 「この機能の境界はどこ？」
- 「何をやって、何をやらない？」
- 「将来的に拡張する可能性は？」

### トレードオフの分析
- 「選択肢Aと選択肢B、どちらが良い？」
- 「それぞれのメリット・デメリットは？」
- 「どのような場合にどちらを選ぶべき？」

### エッジケースの洗い出し
- 「うまくいかない場合は？」
- 「異常系のシナリオは？」
- 「データが大量にある場合は？」

## ドキュメント化のタイミング

### 自動提案するタイミング
- 主要な決定事項が3つ以上出た
- 15分以上の会話が続いた
- ユーザーが「OK」「決まった」などの言葉を使った

### 明示的な保存リクエスト
```
ユーザー: この内容を保存して
ユーザー: ドキュメント化して
ユーザー: まとめて
```

## CLAUDE.mdとの連携

このスキルは、LinkLoomプロジェクトの軽量仕様駆動開発アプローチに従います：

- **保存場所**: `specs/[feature-name]/` または `docs/ai-memo/`
- **ファイル名**:
  - 仕様: `specs/[feature-name]/brief.md`, `design.md`
  - メモ: `docs/ai-memo/YYYY-MM-DD_テーマ名.md`
- **対象コマンド**: `/my:brainstorm`, `/my:design`, `/my:spec-panel`との併用可能

## ベストプラクティス

### ユーザー向け

1. **明確なテーマから始める**: 「〜について考えたい」
2. **率直に話す**: 思いついたことをそのまま話してOK
3. **分からないことは分からないと言う**: Claudeが一緒に考えます
4. **必要に応じてドキュメント参照**: 既存の設計書やコードを参照しながら

### スキル側（Claude）

1. **一度に一つの質問**: 複数の質問を投げない
2. **具体例を出す**: 抽象的な議論は具体例で補足
3. **定期的に要約**: 長い会話は途中で要約する
4. **ジャッジしない**: ユーザーのアイデアを否定しない
5. **代替案を提示**: 複数の選択肢を示す

## トラブルシューティング

### 会話が発散する場合
- 定期的に「これまでの整理」をする
- 優先順位をつける（Must Have vs Should Have）
- 今回の範囲を明確にする

### 決められない場合
- 判断基準を明確にする
- 簡単なプロトタイプで検証する案を提案
- 一旦仮決めして後で見直す

### ドキュメント化が失敗する場合
- `docs/ai-memo/`ディレクトリが存在するか確認
- ファイル名に特殊文字が含まれていないか確認
- 手動で保存先を指定
