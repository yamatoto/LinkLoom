  🔒 セキュリティ: Chrome DevTools MCP環境の改善提案

  ✅ 現状の評価

  開発環境限定で実用上問題なし。ただし、より安全な実装も可能です。

  🌟 推奨アプローチ（3つの選択肢）

  Option A: 本番ビルド時検証（最も手軽）

  // next.config.js
  const nextConfig = {
    // ... 既存設定

    webpack: (config, { isServer, dev }) => {
      // 本番ビルド時にチェック
      if (!dev && !isServer) {
        if (process.env.NEXT_PUBLIC_DEV_AUTH_BYPASS === 'true') {
          throw new Error(
            '🚨 SECURITY: NEXT_PUBLIC_DEV_AUTH_BYPASS is enabled in production build!'
          )
        }
      }
      return config
    },
  }

  利点: 簡単、現状のコードを変更不要欠点: クライアントサイドに環境変数が埋め込まれる（開発ビルドのみ）

  Option B: Server Action経由（Next.js 15推奨）

  // app/actions/auth.ts
  'use server'

  export async function getDevAuthUser() {
    if (
      process.env.NODE_ENV === 'development' &&
      process.env.DEV_AUTH_BYPASS === 'true'
    ) {
      return {
        id: 'dev-user-mock-id',
        email: 'dev@example.com',
        user_metadata: {
          full_name: 'Dev User',
          avatar_url: '',
        },
        app_metadata: {},
        aud: 'authenticated',
        created_at: new Date().toISOString(),
      }
    }
    return null
  }

  // src/hooks/useAuth.ts
  useEffect(() => {
    getDevAuthUser().then(mockUser => {
      if (mockUser) {
        setUser(mockUser as User)
        setLoading(false)
        return
      }

      // 通常のSupabase認証
      supabase.auth.getSession().then(...)
    })
  }, [])

  利点:
  - クライアントサイドに環境変数を公開しない
  - サーバーサイドで完全に制御
  - Next.js 15の推奨パターン

  欠点: 実装変更が必要

  Option C: Cookie/Headerベース

  Middlewareで特殊なCookieを設定し、クライアントで読み取る方法。

  評価: Server Actionの方がシンプルでNext.js 15のベストプラクティス
