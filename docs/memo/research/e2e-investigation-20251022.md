# E2Eテスト不安定性メモ (2025-10-22)

## 概要
2025-10-22 の Playwright 実行 (`npm run e2e:ci`) で 27 件中 5 件失敗。各テストの現状と想定される原因、次回以降の対応方針を整理する。

## 失敗テストと一次調査

### 1. 記事一覧ページ / 記事カードに必要な情報が表示される
- 発生箇所: `tests/e2e/article-list.spec.ts:18`
- 症状: `locator('a[href*="http"]').first().locator('h3')` が見つからずタイムアウト。
- 想定原因:
  - Supabase テスト DB に記事データが存在せず、UI にカードがレンダリングされない。
  - もしくはカード内のタイトルタグが `h3` 以外に変わっている可能性。
- 次回対応案:
  1. シードデータ投入か、E2E 前に記事作成用のセットアップを追加。
  2. DOM 構造が変わっている場合はセレクタを `getByRole('heading', { level: 3 })` 等へ調整。

### 2. 記事登録スモークテスト / 未認証ユーザーは記事登録ページにアクセスできない
- 発生箇所: `tests/e2e/article-registration.spec.ts:36`
- 症状: 未認証コンテキストで `/articles/new` にアクセスしても `/login` へリダイレクトされない。
- 想定原因:
  - `AUTH.PUBLIC_ROUTES` に `/` が含まれているため、`middleware.ts` が `/articles/new` を完全に保護できていない。
  - `/articles/new` ページ自体が `use client` でミドルウェアより後段のチェックに依存している。
- 次回対応案:
  1. `AUTH.PUBLIC_ROUTES` から `/` を除外して保護ルートを明確化（影響調査必須）。
  2. `/articles/new` をサーバーコンポーネント化し、認証失敗時に `redirect('/login')` を行う等のサーバーサイドガードを追加。

### 3. 記事登録スモークテスト / ユーザーが記事を登録できる
- 発生箇所: `tests/e2e/article-registration.spec.ts:44`
- 症状: 送信成功後の URL が期待 (`/`) と一致せずタイムアウト。（現実は `/articles` に遷移している模様）
- 想定原因:
  - 実装が `router.push('/articles')` を行っており、テストの期待値が古い。
  - Supabase への insert が失敗し、リダイレクト前にエラーで止まっている可能性も要確認。
- 次回対応案:
  1. 実装どおりの遷移先 (`/articles`) を期待するか、成功条件をトースト表示などで判定するよう更新。
  2. Supabase 側のシード・テストアカウントの権限を確認し、`createArticle` が成功することを明示的に検証。

### 4. 記事登録スモークテスト / 送信ボタンが無効化されている間はフォームが再送信できない
- 発生箇所: `tests/e2e/article-registration.spec.ts:121`
- 症状: サブミット後に `submit` ボタンやフォームフィールドが disabled 状態にならずタイムアウト。
- 想定原因:
  - `ArticleForm` では `isSubmitting` prop を利用しているが、E2E では Supabase 失敗→ `finally` で `setIsSubmitting(false)` が即実行されているかもしれない。
  - 成功前提のテストのため、上記「記事登録プロセスが成功しない」問題が根本。
- 次回対応案:
  1. `createArticle` 成功を保証するテストシナリオ（スタブ or テスト専用 Supabase データ）を整備。
  2. 成功するまでローディング状態が続くことを検証できるよう、テストの期待条件を調整。

### 5. 認証スモークテスト / ログインページが正しく表示される
- 発生箇所: `tests/e2e/auth-smoke.spec.ts:20`
- 症状: `Googleでログイン` ボタンが見つからず。ページスナップショットではヘッダーが表示されており、すでにログイン済み状態が維持されている。
- 想定原因:
  - ベースフィクスチャ `page` が `storageState` を引き継いでおり、テスト冒頭で既に認証済み。
- 次回対応案:
  1. ログインページ検証用のテストでは `unauthenticatedPage` を使用する。
  2. もしくはテスト冒頭で `await page.context().clearCookies()` → `page.reload()` を実行して未認証状態を作る。

## 共通タスク候補
1. テスト用データ投入のワークフロー整理（Supabase seed or Server Action 直呼び）。
2. Playwright フィクスチャ/ストレージ戦略の見直し。
3. 認証必須ページのサーバーサイドガード整備。
4. テスト期待値の更新（実装と整合を取る）。

## 次回セッションでの推奨アクション
- 上記共通タスク 1 → 2 → 3 → 4 の順で検討すると調査効率が良さそう。
- 着手前に `tests/e2e/global-setup.ts` の再利用ロジックも確認し、余計な再認証を避ける最適化が必要か判断する。
