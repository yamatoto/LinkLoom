  💡 初期仮説：優れたUTの特徴

  あなたの問題意識から、以下のような仮説を立てています：

  ✅ 優れたUTの特徴（仮説）

  1. 価値あるテスト
    - ビジネスロジックと重要な境界条件に焦点
    - 実装の詳細ではなく、動作の保証
  2. 適切なモック戦略
    - 外部依存（API、DB）はモック
    - 内部ロジックは実コード使用
    - モックの粒度を適切に選択
  3. 保守性の高い設計
    - テストケース間の独立性
    - 明確な命名とAAAパターン（Arrange-Act-Assert）
    - 共通設定の適切な抽象化
  4. 変更に強い
    - 実装の変更に影響されない
    - リファクタリングで壊れない
    - APIの振る舞いのみをテスト

  🎯 評価の進め方

  Step 1: 今回のテストコードをレビュー

  まず、実装されたテストを具体的に見て、良い点・改善点を洗い出しましょう。

  Q1: 今回生成されたテストコードを見て、直感的にどう感じましたか？
  - 読みやすい？複雑？
  - 何をテストしているか分かりやすい？
  - このテストがあれば安心してリファクタリングできそう？

  Step 2: 評価軸の定義

  以下の観点で、今回のテストを一緒に評価してみませんか？

  A. テストの目的達成度

  // 例：useAuth.test.ts の signInWithGoogle のテスト
  it('Supabase signInWithOAuthが正しく呼び出される', async () => {
    const response = await result.current.signInWithGoogle()
    expect(mockSignInWithOAuth).toHaveBeenCalledWith({
      provider: 'google',
      options: {
        redirectTo: expect.stringContaining('http://localhost:3000'),
      },
    })
  })

  このテストは何を保証していますか？
  - ✅ Supabase APIが正しいパラメータで呼ばれる
  - ❓ Google OAuth認証が実際に動作する（これは保証できない）

  B. モックの適切性

  今回のテストでは：
  // Supabaseクライアント全体をモック
  vi.mock('@/lib/supabase', () => ({
    supabase: {
      auth: {
        getSession: mockGetSession,
        signInWithOAuth: mockSignInWithOAuth,
        // ...
      },
    },
  }))

  この設計について：
  - 外部サービス（Supabase）をモックしているのは適切？
  - モックの粒度（auth全体 vs 個別メソッド）は適切？
  - もっと良いアプローチはある？

  C. 変更への耐性

  シナリオ：useAuthの内部実装を変更
  // 変更前
  const { error } = await supabase.auth.signInWithOAuth(...)

  // 変更後（リトライロジック追加）
  const { error } = await retryWithBackoff(() =>
    supabase.auth.signInWithOAuth(...)
  )

  Q2: この変更でテストは壊れますか？壊れるべきですか？

  D. 読みやすさと保守性

  // 現在の実装
  describe('エラーハンドリング', () => {
    it('Google認証キャンセル時、適切なエラーメッセージが表示される', async () => {
      const error = createMockAuthError('popup_closed', 400)
      // ... テストロジック
    })
  })

  評価ポイント：
  - テスト名は振る舞いを明確に表現している？
  - テストの構造（Arrange-Act-Assert）は明確？
  - 重複したセットアップコードは適切に抽象化されている？
